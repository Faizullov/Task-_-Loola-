# ReAct-агент для работы с кодом

Агент запускается из командной строки и использует `StateGraph` из LangGraph. Модель выбирает действие, харнесс выполняет вызов инструмента и передаёт результат обратно модели. Цикл завершается, когда модель отвечает без вызовов инструментов или достигнут лимит ходов.

## Ключевые возможности проекта

- **ReAct на LangGraph.** Граф связывает ответы модели, вызовы инструментов и наблюдения. Ответ без вызовов завершает задачу.
- **Ленивая загрузка.** Четыре скилла и шесть инструментов подгружаются по запросу через три постоянные схемы API.
- **Два режима сжатия.** `trim` сохраняет свежую историю в пределах бюджета, `summary` сворачивает старые ходы в сводку. Режим выбирается при сборке агента или через CLI.
- **Стабильный префикс для кеширования.** Активация скилла дописывает сообщения в историю. CLI выводит `cached_tokens`, когда сервер присылает эту метрику.
- **Обработка сбоев.** Модель получает ошибки вызовов и результаты команд. Харнесс ограничивает повторы API, а после переполнения сжимает историю и повторяет запрос к модели.

## Локальный запуск

Понадобятся Python 3.11 или новее, Git, Bash и сервер модели с поддержкой вызовов инструментов через Chat Completions.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

export LLM_BASE_URL="https://example.com/v1"
export LLM_MODEL="your-model"
export LLM_API_KEY="your-api-key"
python agent.py --compaction trim "Найди лимит ходов и проверь синтаксис agent.py"
```

Агент работает в текущем каталоге. Bash запускает команды с правами пользователя, который запустил агента. При первом запуске токенизатор может загрузить словарь.

## Ленивая загрузка скиллов и инструментов

При запуске модель получает название и краткое описание каждого скилла. В поле `tools` каждого запроса передаются три схемы.

| Функция | Что делает |
| --- | --- |
| `bash(command)` | Выполняет команду в рабочем каталоге |
| `load_skill(name)` | Активирует скилл и возвращает его инструкции и схемы инструментов |
| `run_tool(name, arguments)` | Проверяет доступность инструмента, валидирует аргументы и выполняет вызов |

| Скилл | Какие инструменты подключает |
| --- | --- |
| [inspect-project](skills/inspect-project/SKILL.md) | `list_files`, `search_text`, `read_file` |
| [write-tests](skills/write-tests/SKILL.md) | `search_text`, `read_file`, `apply_patch`, `run_checks` |
| [fix-bug](skills/fix-bug/SKILL.md) | `search_text`, `read_file`, `apply_patch`, `run_checks`, `git_diff` |
| [verify-changes](skills/verify-changes/SKILL.md) | `git_diff`, `run_checks` |

Чтобы добавить скилл, создай `skills/<name>/SKILL.md` с полями `name` и `description`. В `metadata.tools` перечисли имена инструментов через пробел. [Реестр инструментов](harness/tools.py)

## Сжатие контекста

Режим задаётся при сборке графа аргументом `compaction`. В командной строке доступны `--compaction trim` и `--compaction summary`.

| Режим | Как работает |
| --- | --- |
| `trim` (по умолчанию) | Удаляет старые завершённые ходы до нужного лимита. Если последний вывод сам превышает бюджет, сохраняет его конец, который помещается в лимит. |
| `summary` | Отправляет старые ходы на суммаризацию отдельным запросом к модели. Обновляет сводку и сохраняет свежие ходы целиком, пока они помещаются в бюджет. |

```python
import os
from pathlib import Path

import tiktoken
from langchain_openai import ChatOpenAI

from agent import MAX_API_RETRIES, SKILLS_DIR, TOOL_SCHEMAS, build_agent, initial_state
from harness.context import ContextBudget
from harness.skills import discover_skills
from harness.tools import Workspace

encoding = tiktoken.get_encoding("cl100k_base")
budget = ContextBudget(32_768, 4_096, None, lambda text: len(encoding.encode_ordinary(text)))
workspace = Workspace(Path.cwd())
skills = discover_skills(SKILLS_DIR)

settings = {
    "model": os.environ["LLM_MODEL"],
    "base_url": os.environ["LLM_BASE_URL"],
    "api_key": os.environ["LLM_API_KEY"],
    "use_responses_api": False,
    "max_retries": MAX_API_RETRIES,
}
chat_model = ChatOpenAI(**settings, max_tokens=budget.output_tokens)
summary_model = ChatOpenAI(**settings, max_tokens=budget.summary_tokens)
call_model = chat_model.bind_tools(TOOL_SCHEMAS).invoke
trim_graph = build_agent(call_model, workspace, skills, budget, compaction="trim")
summary_graph = build_agent(
    call_model, workspace, skills, budget,
    compaction="summary", summarize=summary_model.invoke,
)
result = summary_graph.invoke(initial_state("Изучи структуру проекта"))
print(result["response"].text)
```

По умолчанию сжатие запускается, когда оценка размера полного запроса превышает 90% окна, оставшегося после резерва на ответ. В оценку входят история, системный промпт, исходная задача и схемы инструментов. В обоих режимах харнесс хранит исходную задачу и список активных скиллов, а вызовы инструментов обрабатывает вместе с их результатами. При ошибке переполнения харнесс сильнее сжимает историю и один раз повторяет запрос к модели. Уже выполненные команды при этом не запускаются повторно. [Реализация сжатия](harness/context.py)

| Переменная окружения | Значение по умолчанию |
| --- | --- |
| `LLM_CONTEXT_WINDOW` | `32768` токенов на вход и ответ вместе |
| `LLM_MAX_OUTPUT_TOKENS` | `4096` токенов в резерве на ответ |
| `LLM_HISTORY_TOKENS` | По умолчанию не задан. Можно установить отдельный лимит истории для стресс-теста |
| `LLM_TOKEN_ENCODING` | `cl100k_base` для локальной оценки |
| `LLM_MAX_TURNS` | `200` ходов модели |

Локальная оценка токенов может отличаться от подсчёта сервера. Размер окна и токенизатор задаются под используемую модель.

## Кеширование промпта

В начале каждого запроса идут фиксированный системный промпт с кратким каталогом скиллов и исходная задача. Три схемы инструментов передаются в том же порядке. Полные инструкции и схемы инструментов скилла добавляются в конец истории как результат `load_skill`. Харнесс хранит `active_skills` в состоянии графа для проверки доступа и добавляет список в сводку при сжатии в режиме `summary`. [Сборка префикса](agent.py#L98)

В режиме `summary` история меняется с места вставки сводки. Системный промпт, исходная задача и схемы остаются пригодны для повторного использования сервером. Между сжатиями запросы снова растут добавлением новых сообщений в конец. CLI выводит `[cache] cached_tokens=…` в `stderr`, когда сервер отдаёт число токенов из кеша. [OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching) · [vLLM Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)

## Обработка ошибок

| Ситуация | Как обрабатывается |
| --- | --- |
| Битый JSON, неверный тип, неизвестный инструмент или скилл ещё не активирован | Харнесс возвращает короткий `ToolMessage` со статусом `error`. Модель может исправить вызов. |
| Тест упал, Git отклонил патч, команда вернула ненулевой код | Харнесс помечает `ToolMessage` как `error` и передаёт модели код выхода и фрагмент вывода. |
| Таймаут команды | Харнесс прерывает ожидание через 120 секунд. В сообщении модели указано, что команда могла изменить файлы и перед повтором нужно проверить рабочий каталог. |
| Переполнение контекста | Харнесс сжимает историю и один раз повторяет запрос к модели. |
| Временный сбой API | Клиент может повторить запрос до двух раз. Повтор касается только запроса к модели. |
| Ошибка авторизации или некорректная конфигурация скиллов | Запуск завершается с диагностикой. Ссылки на незарегистрированные инструменты проверяются при сборке графа. |

## Тесты

Тесты с имитацией ответов модели проверяют активацию скиллов, неизменность префикса, `cached_tokens`, ошибки инструментов, оба режима сжатия и повторы API.

```sh
python -m unittest discover -s tests -v
```

## Восстановление и оценка контекста

Пустой ответ без текста и инструментов или незавершённый ответ с
`finish_reason=length` запускает повтор запроса к модели.
Допускается два повтора, после которых агент завершается с явной ошибкой.
Ранее выполненные инструменты при этом повторно не вызываются.

Локальная оценка контекста корректируется коэффициентом из фактического
`prompt_tokens` сервера. Коэффициент хранится в состоянии каждого прогона.
Сжатие учитывает эту поправку и сохраняет исходный префикс запроса.

В режиме `summary` после сжатия остаётся примерно половина доступного бюджета
под свежую историю. Суммаризатор читает старую историю порциями до 4096
скорректированных токенов. В сводке сохраняются требования, изменения,
результаты проверок и оставшиеся действия. Для пустого ответа суммаризатора
тоже допускается два повтора.

## Бенчмарк миграции Python-плагинов

Сценарий в `benchmarks/plugin_project` содержит 12 Python-модулей. Нужно
привести обработку строк JSON во всех модулях к контракту, сохранив порядок,
дубликаты и типы идентификаторов, включая целый ноль. Агент исправляет код,
добавляет тесты и проходит объёмные интеграционные проверки.

Вывод проверок содержит синтетические трассы. Это сценарий для исследования
длинной истории инструментов. Требования находятся в `contract.md`,
автоматическая оценка проверяет их после завершения агента.
Старые сценарии и таблицы результатов удалены из проекта.

```sh
python bench.py --variants legacy summary --runs 1 --max-turns 200 --reasoning-effort none --output benchmark-results/migration
```

Оба варианта используют одну модель `gemma4:12b`, температуру 0,1, резерв
ответа 2048 токенов и окно 32768. Отдельный низкий лимит истории выключен.
Запросы суммаризатора входят в расход токенов. В `runs.jsonl` сохраняются
результаты по каждому модулю, расход, пик входного контекста и число сжатий.
Полный успех требует прохождения всех 12 модулей и добавленных регрессионных тестов.

### Результаты сравнения после правок

Одна попытка на вариант в каждом из двух исследованных вариантов трасс.
Лимит 200 ходов, Python 3.12.16, Gemma 4 12B, окно 32768, температура 0,1.
Счёт отражает 12 модулей и обязательные добавленные регрессионные тесты.
Все ответы API, включая суммаризатор и восстановление после пустых ответов,
включены в расход. Исходные метрики сохранены в [results.json](benchmarks/results.json).

| Трассы | Харнесс | Проверок | Входных токенов | Выходных токенов | Сжатий |
| --- | --- | ---: | ---: | ---: | ---: |
| Хеши запросов | legacy | 2/13 | 165531 | 2582 | 0 |
| Хеши запросов | summary | 0/13 | 23382 | 2178 | 0 |
| Читаемые тестовые случаи | legacy | 1/13 | 14186 | 2514 | 0 |
| Читаемые тестовые случаи | summary | 12/13 | 795830 | 15578 | 3 |

### Почему получился такой результат

**Legacy рано завершил цикл.** В прогоне с читаемыми трассами сервер вернул
`finish_reason=length` и служебный текст `thought <channel|>` без вызова
инструмента. Исходный цикл трактует любой ответ без инструментов как завершение.
К этому моменту был исправлен один модуль. Пиковый вход этого прогона составлял
4577 токенов, поэтому причина зарегистрированной остановки относится к
незавершённому ответу модели. В прогоне с хешами пик legacy достиг 31974 токенов.
Оба прогона завершились с `output_limit`. Ошибок переполнения сервер не прислал.

**Новый харнесс смог продолжить работу.** После семи пустых или незавершённых
ответов он снова запрашивал действие модели. В результате выполнил 48 основных
запросов и исправил все двенадцать модулей. Такая обработка ответов непосредственно
присутствует в журнале этого прогона.

**Сжатие поддержало длинную историю.** Оно сработало после 23-го, 32-го и 45-го
хода. Суммаризатор заменял старые ходы сводкой требований, изменений и результатов
проверок. При коэффициенте поправки локальной оценки около 1,16 пик фактического
входа нового варианта составил 26203 токена при окне 32768.
Этот прогон измеряет совместную работу восстановления и сжатия.
Для отдельной оценки вклада сводки требуется контрольный прогон с тем же
восстановлением и выключенной суммаризацией.

**Расход вырос вместе с объёмом выполненной работы.** Legacy остановился после
6 запросов. Новый вариант сделал 48 основных и 15 запросов суммаризатора.
Входные 795830 токенов — сумма по всем 63 ответам API, включая повторно
отправляемую историю. Пик одного входного запроса составлял 26203 токена.
В режиме суммаризации значительная часть расхода связана с повторной передачей
контекста и дополнительными запросами для сводки. Сравнение расхода этих
прогонов учитывает разный объём завершённой работы.

**Обязательные тесты остались невыполненным пунктом.** Новый агент в финальном
ответе заявил о добавлении регрессионных тестов. В рабочем каталоге появились
только изменения двенадцати модулей, а проверка unittest обнаружила 0 тестов.
Поэтому итоговый счёт — 12/13, полный успех — 0/1. У legacy счёт 1/13 и
полный успех тоже 0/1.

**Границы измерения.** В этих прогонах модель использовала `bash`.
Загрузок скиллов и вызовов `run_tool` было 0. Ленивая загрузка проверяется
автоматическими тестами харнесса, а её вклад в эффективность здесь отдельно
не измерялся. Между двумя наборами трасс изменились и формат вывода, и
обработка незавершённых ответов нового харнесса. Каждый вариант запускался
один раз, сценарии подбирались для исследования длинного контекста.
Наблюдаемое преимущество последнего прогона относится к числу исправленных
модулей и возможности продолжить задачу. Полных успешных прогонов в обоих
сравнениях нет. Исходные метрики доступны в [results.json](benchmarks/results.json).
